# Async Event Schema Definition

Complete event contract definitions and lifecycle management for [PROJECT] asynchronous architecture.

## Event Naming Convention

All events follow the pattern: `domain.entity.verb`

Format: `{domain}.{entity}.{verb}`

**Examples:**
- `auth.user.registered`
- `auth.user.password_reset`
- `payment.invoice.created`
- `payment.invoice.paid`
- `notification.email.sent`
- `notification.email.failed`

**Guidelines:**
- Domain: lowercase, singular (auth, payment, notification, order, inventory)
- Entity: lowercase, singular (user, invoice, email, product)
- Verb: lowercase, past-tense (created, updated, deleted, sent, failed, completed)
- Never use dots in any component (use underscores for multi-word names)

## Event Envelope Format

All events wrapped in standard envelope for routing, tracking, and replay:

```json
{
  "id": "evt_1234567890abc",
  "type": "auth.user.registered",
  "timestamp": "2024-01-15T10:30:45.123Z",
  "version": "1",
  "source": "auth-service",
  "source_region": "us-east-1",
  
  "data": {
    // Event-specific payload (defined per event type)
  },

  "metadata": {
    "trace_id": "tracing-123456",
    "correlation_id": "corr-789012",
    "user_id": "user_123",
    "request_id": "req_456789",
    "idempotency_key": "idem_abcdef",
    "retry_count": 0,
    "tags": ["production", "critical"]
  }
}
```

### Envelope Fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `id` | string | Yes | Unique event ID (format: evt_*) - generated by publisher |
| `type` | string | Yes | Event type in domain.entity.verb format |
| `timestamp` | string | Yes | ISO 8601 UTC timestamp when event occurred |
| `version` | string | Yes | Schema version (for backward compatibility) |
| `source` | string | Yes | Service that published the event |
| `source_region` | string | No | Geographic region where event originated |
| `data` | object | Yes | Event-specific payload |
| `metadata` | object | Yes | Operational metadata |

### Metadata Fields

| Field | Type | Required | Description |
|-------|------|----------|-------------|
| `trace_id` | string | No | Distributed tracing ID |
| `correlation_id` | string | No | Correlation across related events |
| `user_id` | string | No | User who triggered the event |
| `request_id` | string | No | Originating HTTP request ID |
| `idempotency_key` | string | No | Idempotent event replay key |
| `retry_count` | integer | Yes | Number of delivery retries (0 = first attempt) |
| `tags` | array | No | Custom tags for filtering/routing |

## Dead Letter Queue (DLQ) Strategy

### DLQ Architecture

Events that fail processing are moved to a dead letter queue for analysis and manual intervention.

```
Event Stream → Consumer → Success?
                  ↓ (failure after max retries)
              Dead Letter Queue → Analysis → Manual Replay
```

### DLQ Configuration

```json
{
  "max_retries": 5,
  "retry_delay_ms": 1000,
  "max_retry_delay_ms": 300000,
  "backoff_multiplier": 2.0,
  "dlq_retention_days": 30
}
```

### DLQ Entry Schema

```json
{
  "dlq_id": "dlq_abc123def456",
  "original_event": { /* full event envelope */ },
  "last_error": {
    "message": "Failed to process payment",
    "code": "PAYMENT_GATEWAY_TIMEOUT",
    "stack_trace": "...",
    "timestamp": "2024-01-15T10:30:45.123Z"
  },
  "retry_attempts": 5,
  "first_failure_at": "2024-01-15T10:28:00.000Z",
  "last_failure_at": "2024-01-15T10:30:45.123Z",
  "consumer_service": "subscription-service",
  "status": "pending_manual_review"
}
```

### DLQ Processing

```bash
# Query DLQ for failed events
SELECT * FROM dlq WHERE status = 'pending_manual_review' 
  ORDER BY first_failure_at DESC;

# Manual replay (after investigation and fix)
npm run dlq:replay -- --dlq_id=dlq_abc123def456

# Discard event after review
npm run dlq:discard -- --dlq_id=dlq_abc123def456
```

## Idempotency Requirements

All event consumers MUST be idempotent: processing the same event multiple times produces the same result as processing it once.

### Idempotency Implementation

```typescript
// Example idempotent event handler
async function handlePaymentPaid(event: PaymentEvent) {
  const idempotencyKey = event.metadata.idempotency_key;
  
  // Check if already processed
  const existing = await db.query(
    'SELECT id FROM processed_events WHERE idempotency_key = ?',
    [idempotencyKey]
  );
  
  if (existing) {
    console.log('Event already processed, skipping');
    return;
  }
  
  // Process event
  await db.updateInvoice(event.data.invoice_id, { status: 'paid' });
  
  // Record idempotency key
  await db.query(
    'INSERT INTO processed_events (idempotency_key, event_id, processed_at) VALUES (?, ?, ?)',
    [idempotencyKey, event.id, new Date()]
  );
}
```

### Idempotency Key Generation

Idempotency keys are generated by the event publisher and immutable for the event's lifetime:

```typescript
const idempotencyKey = `${event.data.primary_entity_id}:${event.timestamp}:${event.data.operation_type}`;
```

## Event Ordering Guarantees

### Ordering Levels

| Level | Guarantee | Use Case | Trade-offs |
|-------|-----------|----------|-----------|
| **None** | No ordering | Cache invalidation, analytics | Highest throughput |
| **Per-Entity** | Events for same entity processed in order | Payment processing, resource updates | Throughput per entity |
| **Global** | All events processed globally in order | Audit logs, financial transactions | Lowest throughput |

### Implementation

```yaml
# In event broker config
events:
  payment.invoice.paid:
    ordering: per-entity
    partition_by: invoice_id
    max_parallel_partitions: 100
```

## Event Schema Evolution

### Versioning Strategy

Events include a `version` field for safe schema changes:

```json
{
  "type": "auth.user.registered",
  "version": "2",
  "data": {
    "user_id": "user_123",
    "email": "user@example.com",
    "new_field_v2": "value"
  }
}
```

### Backward Compatibility Rules

1. **Never remove fields** - mark deprecated instead
2. **Always provide defaults** - for new fields in old versions
3. **Use feature flags** - gate new behavior on field presence

### Migration Path

```typescript
// Handler supports multiple versions
function handleUserRegistered(event: Event) {
  const payload = event.data;
  
  // Handle v1 and v2
  const email = payload.email || payload.legacy_email;
  const country = payload.country || 'US'; // Default for v1
  
  // Process...
}
```

## Best Practices

1. **Immutable Events:** Never modify event payload after publishing
2. **Fat Events:** Include sufficient context to avoid downstream queries
3. **Graceful Degradation:** Consumers handle unknown event versions
4. **Ordering Intent:** Explicitly declare ordering requirements per event type
5. **Replay Capability:** Store full event history for debugging and replay
6. **Monitoring:** Track DLQ, lag, and consumer health per event type
7. **Documentation:** Keep event schema docs in sync with code
